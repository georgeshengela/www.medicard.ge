## Sign in with Apple / Google (2026-10-01, train 1.0.0.18 — store build)

Native modules `expo-apple-authentication` (iOS) and `@react-native-google-signin/google-signin` (iOS + Android), so this ships only with a store build of train 1.0.0.18, never by OTA. App: `src/lib/socialSignIn.ts` (lazy native requires; cancelled sheet = `null`, not an error), `SocialAuthButtons` on sign-in and sign-up (Apple black/white per HIG, Google white + four-colour G, same size — App Review 4.8), `/(auth)/link-account`. Google OAuth clients (project medicard-d6ea0, created 2026-10-01: Web, iOS, Android for the EAS upload SHA-1; add one more Android client with the Play App Signing SHA-1 after the first Play upload — app „MEDICARD AI“ in the Gamoiwere Play account) — ids live in `mobile/google-oauth.json` (public ids; `app.config.js` adds the Google plugin with the reversed iOS id only once it is set — changing it is native); the Google button hides until configured. Server: `src/lib/socialAuth.js` verifies ID tokens against Apple/Google JWKS (RS256 only, issuer, audience = our own Google Web + iOS client ids `DEFAULT_GOOGLE_CLIENT_IDS` (override `GOOGLE_CLIENT_IDS`) / `APPLE_BUNDLE_IDS`), Apple tokens must carry our HMAC nonce (`GET /api/auth/apple/nonce`). Identities: table `AuthIdentity` (provider + `sub`, never keyed by email; `install-auth-identity.mjs` in `db:install`). **Linking rule:** email sign-up never verified addresses, so a provider email matching an existing password account is NOT linked automatically — 409 `SOCIAL_LINK_REQUIRED` + 10-min `linkToken`, the person enters that account's password once (`POST /api/auth/social/link`). Auto-link only when the account already has another provider identity with the same verified email. Apple without an email → `apple.<hash>@apple.medicard.ge` (synthetic, never mailed). Account deletion revokes Apple grants first (`revokeAppleGrantsForUser`, needs `APPLE_TEAM_ID` / `APPLE_KEY_ID` / `APPLE_PRIVATE_KEY`; App Review 5.1.1(v)). Never weaken the linking rule or accept another app's audience. Tests: `server/src/lib/socialAuth.test.js`.

Web `/app` (2026-10-05): the same endpoints from `server/public/app/js/social.js` on the sign-in, email and sign-up screens; `GET /api/auth/social/config` says which buttons exist. Google = Google Identity Services button with the Web client id (`GOOGLE_WEB_CLIENT_ID`, default the first Google id); it needs `https://medicard.ge` (and www) as Authorized JavaScript origins of that client (set 2026-10-05) and is removed when Google has not drawn it within 10 s — never hide it while waiting, Google does not draw a hidden button. Apple = Sign in with Apple JS (popup) and appears only when Render has `APPLE_WEB_SERVICE_ID` (a Services ID grouped under ge.medicard.app, domain medicard.ge, return URL `APPLE_WEB_REDIRECT_URI`, default `https://medicard.ge/app`); the Services ID joins the accepted Apple audiences, and its refresh token is stored as `<clientId>
<token>` so revoke uses the right client (bare tokens = the bundle id). `/app` answers with `Cross-Origin-Opener-Policy: same-origin-allow-popups` and `Referrer-Policy: strict-origin-when-cross-origin`, and the CSP allows accounts.google.com / appleid.cdn-apple.com — the popups and the Google button need them. A 409 SOCIAL_LINK_REQUIRED opens the same one-time password step as the app.

## One account, many sign-in methods (owner 2026-10-05, app 1.0.0.21.9)

A person signed up on the web with a phone and again in the app with an email: two accounts (fixed by hand — the empty web one was deleted, its phone moved). Rules now (`server/src/lib/accountLogins.js`, tests `accountLogins.test.js`):
- **Same sign-in everywhere:** app sign-in and web `/app` both show Apple / Google, then a Phone | Email switch (last method on the device first; otherwise phone in Georgian, email in English — only Georgian numbers get the SMS). Phone sign-in creates an account for a new number on both. `/(auth)/phone` redirects to `sign-in?method=phone`; sign-up links to it.
- **Sign-in methods on one account:** Profile → „შესვლის გზები“ (`mobile/app/profile/sign-in-methods.tsx`, web `accountLinks.js` card on the profile page): phone (`/profile/verify-phone`), email + password for accounts with a synthetic address (`/profile/add-email`, 6-digit code by email, template `email_verify`, raw-SQL `EmailVerification` created lazily), Apple / Google (`POST /api/auth/{apple,google}/link`). `GET /api/auth/methods` returns `{ phone, email (real only), apple, google }`.
- **Conflict instead of „taken“:** a proven phone / email / Apple / Google that sits on another account answers 409 with `conflict` (`PHONE_TAKEN` / `EMAIL_TAKEN` / `SOCIAL_TAKEN`, 15-min token bound to both accounts). `POST /api/auth/account-conflict/resolve` `move_here` brings every sign-in method of the other account here and deletes it — only when it holds no health content (`CONTENT_TABLES`; automatic rows like HealthProfile, step syncs, generated nutrition plans do not count); `switch` signs in to the other account and deletes this one only when it is empty, otherwise both stay (both with data → „write to support“). Methods are never overwritten: a different phone or a different real email on the kept account blocks the move. Health data is never merged or deleted by this flow; self-service actions are written to `AdminAuditLog` (`USER_LOGINS_MOVED_HERE`, `USER_SWITCHED_ACCOUNT`). `/phone/link/start` no longer refuses a taken number (the OTP is the proof); `/phone/link/verify` also checks the OTP was requested by this account.
- **First question of a new account:** app onboarding (`ExistingAccountCheck`) and web onboarding ask „MEDICARD უკვე გამოგიყენებია?“ once on an account under 24 h old that has not started onboarding; „კი“ calls `POST /api/auth/me/discard-new` (only ≤ 24 h and no health content, no deletion email) and returns to sign-in.

## Phone verification gate (2026-09-27, app 1.0.0.13.14)

Owner-approved: a verified phone is required only where abuse or real value is at stake. Server middleware `requireVerifiedPhone` (`server/src/lib/phoneGate.js`) answers 403 `PHONE_VERIFICATION_REQUIRED` on women's-space join / post / comment and `POST /api/rewards/:id/redeem` (partner vouchers included); apply it to referral rewards and family members when those ship. `User.phone` is only written after an OTP check (or by an admin); email `/register` ignores any `phone` field (2026-09-27 review fix), so a stored Georgian mobile counts as verified. The app catches the code (`mobile/src/lib/phoneGate.ts`) and offers `/profile/verify-phone` (number → SMS code, keyboard-safe shell) instead of an error. Never gate everyday health features (Medi, meds, nutrition, lab, cycle, pets).

## Registration and „დაასრულე პროფილი“ (owner 2026-10-11 rework)

The owner called the old flow „საშინელება“: the phone sign-up never asked the name, „რისთვის გჭირდება MEDICARD?“ was pointless, „დაასრულე პროფილი“ walked every later question again (meds asked twice), skipped the name and restarted the whole list from „შეცვლა“, and the habit questions were vague (fitness 1–5 with „2–3 times a week“ hints, sleep levels with hour hints, three smoking answers, four diets). Rules now:
- **Registration** (`/(auth)/assessment`, velvet like sign-in, `OnboardingKit`): `ExistingAccountCheck` on a fresh account → **name page** only when the sign-in brought no first + last name (`hasFirstAndLastName`: phone, Apple without a name or with a given name only — a known first name is prefilled) — the sign-up look (`VelvetAuthHeader` „როგორ გქვია?“, first + last name, both 2+ letters, saved with `PATCH /api/auth/me` + `extraAnswers.legalName`) → sex → birth date („დაბადების თარიღი“, 18+) → **height** → **weight** (two pages, owner: one page for both looked crowded). Keys `o0-name`, `o1-gender`, `o3-birthdate`, `o4-height`, `o4-weight` (`ONBOARDING_STEP_KEYS`; retired keys resume via `onboardingResumeQuestion`). Then privacy + AI consent, notifications, Home layout (all velvet through `ProfileSetupShell velvetStep`), then the heartbeat disc while the final save runs. **No goal question** and no goal step (first medication / target weight / last period) — the Home layout pick personalises Home; `extraAnswers.primaryGoal` stays readable for older accounts only. Web `/app` onboarding matches (first + last name, no goal).
- **„დაასრულე პროფილი“** (`/profile/complete` → `ProfileQuestionnaire`): walks only unanswered questions of `PROFILE_QUESTIONS` (name if missing, blood type with „არ ვიცი“ = `UNKNOWN` and the Georgian I–IV ↔ O/A/B/AB guide under it, allergies, conditions gate → list, medications gate → list, activity, sleep, smoking, alcohol, diet, fruit/veg + habits), then one summary page; every summary row edits only itself and comes back (`mode.kind === 'edit'`). Active MEDIPILL medicines count as answered (`answeredQuestions(…, { pillCount })`) and the row opens MEDIPILL. Each answer writes only its own fields (`questionPayload`). Never re-introduce mood, checkup frequency or „health goals“ questions.
- **Way-of-life questions** (`src/lib/healthHabits.ts`, research brief 2026-10-11): activity = days a week with 30+ min that raise breathing, any movement counts (adapted Milton item; 5+ ≈ WHO 150 min) + how often exercise/sport; sleep = hours in 24 h (BRFSS: ≤5…10+) + quality (PSQI); tobacco = every day / sometimes / used to / never (NHIS; „sometimes“ = e.g. two cigarettes a month, `smokingStatus: 'OCCASIONAL'`) + products (cigarettes, IQOS/glo, e-cigarette, „ჩილიმი“ — never „კალიანი“); alcohol = how often only (AUDIT-C Q1; the owner dropped the „6+ drinks at the supra“ follow-up); diet = patterns incl. church fasting (multi; „ყველაფერს ვჭამ“ goes with fasting, not with a food restriction) + fruit/veg portions and salt / sugary drinks / sweets / fast food / skipped meals / late eating. Exact answers in `extraAnswers`; the columns Medi and MEDIFOOD already read (`activityLevel`, `exerciseFrequency`, `sleepHours`, `sleepQuality`, `smokingStatus`, `alcoholUse`, `dietType`) are derived. Old vague answers (`fitnessLevel`, `sleepLevel`, `checkupFrequency`, old `dietType`) are not reused — the question is asked again.
- Medi's account-holder block lists them in words (`server/src/lib/lifestyleProfile.js`, never raw enums). The server accepts `smokingStatus: 'OCCASIONAL'` (profile route + Medi's catalogue) — deploy the server before an app build that sends it.
- Georgian copy: no „X-ისა და Y-ის“ constructions (owner: „ხილისა… არაა სწორი ქართული“); keep option labels short and spoken.
- Tests: `npm --prefix mobile run test:onboarding` (`tests/onboarding-flow.test.cjs`, `src/lib/healthHabits.test.ts`), server `src/lib/lifestyleProfile.test.js`.

## Referral · Medi coins (simplified 2026-10-05, app 1.0.0.21.6)

Owner: simple and instant. Tables `ReferralCode` / `Referral` (additive, `install-referral.mjs` in `db:install`). A person with a verified phone sees a personal 6-character code on Profile → „მოიწვიე მეგობარი“ (copy button + share; the share text says where to enter it). A new account (≤ 14 days) enters a friend's code once at `/profile/invite-code` (row „მოწვევის კოდი მაქვს“, deep link `medicard://invite/CODE`, web `https://medicard.ge/i/CODE` prefills it) and **both sides get 25 Medi coins in the same transaction** (`RewardLedger` `sourceType REFERRAL`, `invitee:`/`inviter:` ids; the claim answers with the new balance). No phone or first health action is required from the invitee any more. Limits: **5 invites per code per Tbilisi calendar month** (row lock on the inviter's `ReferralCode`, shown on the page as „ამ თვეში N/5“), one device per referral (hashed install id, required), 3 per inviter per network per 30 days. The inviter's page lists who joined as first name + last initial (`inviteeLabel`; the entry screen says so). Admin switch `referralRewards` off = claims are kept PENDING and `processPendingReferrals` (10-min lease job) pays them when it is back on. No monetary value — never add cash-out; store redemption still needs a verified phone. Admin: Rewards → მოწვევები. Tests: `server/src/lib/referral.test.js`.
