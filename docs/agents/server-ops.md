## Health-sync loop incident + voice speed (2026-09-29, app 1.0.0.17.12)

Owner saw the server "fall over" while using the voice assistant. Render logs + `CapacitySample` showed one phone sending 979 → 1 788 → 3 354 requests/min (CPU 94 %, 270 in flight): a feedback loop, not the assistant. Every `POST /api/health-metrics/sync` emitted socket `health:metrics`; the app answered with `requestHealthRefresh` → every mounted steps/metrics/hydration hook re-read the device (`force`) and synced again → more events, multiplied by each open screen. Guards now (keep all three): server — `/sync` per-user limit 30/min, writes/emits/Quest recompute only when a value actually changed, `emitUserHealthMetrics` coalesced to ≤1 per 3 s per user; app — `requestHealthRefresh` coalesced (1.5 s), socket echo of this device's own sync ignored for 5 s (`isOwnHealthEcho`), identical payloads never re-pushed, device pushes ≤1 per 20 s (`syncNativeHealthToServer`). Never make a socket event trigger a write without these guards.

Voice turn latency (logs: transcribe 4–5 s, plan 4–7 s, speak 1.5–4 s): no extra model call to pick context (`assistantDefaultDomains`), the planner's static system prompt comes first (provider prompt cache) with clock/subject/context in a second system message, recording is speech-grade (16 kHz mono 32 kbps AAC), and recording ends automatically ~1.6 s after the person stops speaking (adaptive noise floor in `useAssistantVoice`); releasing still sends at once.

## Loop guard (2026-09-29, app 1.0.0.17.13)

Two nets for request loops nobody has found yet (after the health-sync incident). App: `mobile/src/lib/requestBreaker.ts`, checked in `request()`, native uploads and `pulseApi` via `guardRequest` — the same method+path+query more than 30× in 10 s is refused locally for 30 s (429 `CLIENT_LOOP_GUARD`), more than 300 requests of any kind in 10 s pauses everything for 30 s; each trip is reported once per 5 min to `POST /api/app/client-guard` (route template only, ids → `:id`, no query). Server: `server/src/lib/loopGuard.js` — a per-session ceiling of 600/min on all of `/api` (`user-ceiling`), keyed by session token hash, guests never counted. This is the only allowed exception to "no global /api limiter": never lower it towards real traffic or key it by IP. Both paths send a throttled Director Telegram notice (search Render logs for `[loop-guard]`). A trip means an app bug: find and fix the loop, do not raise the limits.

Audit follow-ups (1.0.0.17.14): foreground work uses `onReturnToForeground` (`src/lib/appForeground.ts`, background → active only — iOS inactive → active from Face ID / permission sheets / Control Center is not a return); `runPostLoginSideEffects` runs once per account per 5 min unless `force` (sign-in); `runMediNotificationBrain` ≤1/min with one trailing run (`force` for settings changes); push register skips an unchanged token for 6 h; `requestQuestRefresh` is coalesced (300 ms) and socket reconnects refresh with 0–4 s jitter; MEDIRUN background uploads back off 5 s → 5 min; GETs replay once only on 502 (never 503/504). Server: AppSettings cached 10 s, AI daily fuses in `server/src/lib/aiDailyCap.js` for routes outside `enforceAiQuota`, `PHARMACY_SYNC_IN_WEB=off` moves the Playwright scrape out of the web process (only once the cron service is confirmed). New AppState / socket handlers must follow the same rules.

## Server capacity alerts (2026-09-28)

Owner wants to scale Render before the server falls over. `server/src/lib/capacity.js` (production only; `CAPACITY_MONITOR=off` disables) samples each instance once a minute — CPU vs cgroup limit, memory vs limit, event-loop p95, GET `/api` p95 (AI answers/uploads are POST and excluded), 5xx %, DB ping — into `CapacitySample` (7 days) via `prisma/20260928-capacity.sql` / `install-capacity.mjs` in `db:install`. ## Error monitoring (2026-09-29)

Self-hosted instead of Sentry: `server/src/lib/errorMonitor.js`, table `ErrorEvent` (`prisma/20260929-errors.sql`, `install-errors.mjs` in `db:install`). Inputs: the app's `POST /api/app/client-error` (no auth; a valid user Bearer only attributes the events — never a user id from the body; headers `X-Medicard-Platform` / `X-Medicard-App-Version`; body `{ events: [{ kind: crash|error|unhandled_rejection|render, name, message, stack?, route?, fatal?, at? }] }`, ≤10 events (extra ignored), 202 / 400, own limit 20/min per IP), every unhandled 500 in `middleware/error.js` (fire-and-forget) and `uncaughtException` / `unhandledRejection` in `server.js` (log, record, still exit 1 — up to 2 s later to flush). Scrubbing before storage: message ≤300, stack ≤15 frames as `function (file:line)` with basenames, emails → `[email]`, ≥7-digit runs → `[num]`, JWT/long tokens → `[token]`, UUID/cuid → `:id`, routes via `routeTemplate` (no query); user = 16-hex sha256 hash. Never add bodies, query strings or health data. Fingerprint = sha1(source|kind|name|normalized message|first own frame without line number). Per instance: one row per fingerprint per 10 s (repeats fold into the next row's `count`), ≤500 rows/min. Director Telegram: new fingerprint (not seen in 7 days; ≤1/6 h each, ≤10/h) and spike (>50 in 10 min; ≤1/2 h each); throttles are in memory per instance. Recording is production-only (`ERROR_MONITOR=off|on`); rows purged after 30 days under the `error-events-purge` lease. Admin `#/errors` (შეცდომები, `g g`, `v4/modules/errors.js`, `/api/admin/errors`, `/api/admin/errors/:fingerprint`).

## AI answers that cannot hang (2026-10-14)

Incident: a Medi question waited 142 s with no word — the Gemini call through OpenRouter went to the one host we allow (`google-vertex/global`, `allow_fallbacks: false` for ZDR/no-training), that host stalled, and the EvidenceMD safety net answered `402 Insufficient credits`; the person saw „სამედიცინო ანალიზის სერვისთან დაკავშირება ვერ მოხერხდა“ and a manual retry answered in 12 s. The log only had our generic Georgian line, never the provider's reason.

- **Two queues on the same disclosed host.** `aiDisclosure.json` `routing` for Gemini lists `google-vertex/global` then `google-vertex/global/priority` (Vertex priority tier: same Google Vertex recipient, ZDR, ~1.8× price — no consent change). Every request may fall to priority when standard *errors* (OpenRouter, manifest order). `approvedProviderRouting(model, route)`: the `x-medicard-ai-route: priority` header (`AI_ROUTE_HEADER`, stripped in `consentedAiFetch`) puts the priority host first.
- **Race, not wait** (`askAi` → `askOpenRouterRaced`, timings in `AI_ANSWER_TIMING`): streamed — no word in 20 s (or an error before any word) → the same request also goes to priority; the first to write wins, the other is aborted; neither wrote by 60 s → EvidenceMD (60 s budget) → `AI_STALLED` „Medi-მ დროულად ვერ უპასუხა“. Words started, then 45 s of silence → `AI_STALLED` „…შუაში შეწყდა“, never swapped (she already read them; the app puts the question back). Unstreamed — hedge at 45 s, give up at 120 s. A person who leaves aborts everything; no hedge starts after that.
- **Cause on record.** `upstreamDetail(error)` (status · error name · provider · message ≤140) rides on errors as `adminDetail`; `runTrackedAi` stores `message — adminDetail` in `AiInteraction.errorMessage`; Render logs `[medicard] openrouter attempt failed {route, ms, detail}`, `ai hedge → priority`, `ai answered after hedge`. Answers from the priority queue are logged as `reasoningModel` `google/gemini-3.8-flash · priority`, so admin's model counts show how often it was needed.
- **EvidenceMD credits:** a 402 sends a Director Telegram notice (`notifyOwner`, `system`, ≤1 per 6 h per instance) — top up at evidencemd.ai/developers/dashboard. Tests: `aiEngine.test.js` (race, stall, abort, broken Georgian), `aiConsent.test.js` (priority routing never leaks the header).
