# Server: loops, cache, installs, email, support, capacity, errors, module switches, news

Moved verbatim from AGENTS.md on 2026-10-08 (token diet). Read this file before working in its area; add new notes here, not in AGENTS.md.

## Health-sync loop incident + voice speed (2026-09-29, app 1.0.0.17.12)

Owner saw the server "fall over" while using the voice assistant. Render logs + `CapacitySample` showed one phone sending 979 → 1 788 → 3 354 requests/min (CPU 94 %, 270 in flight): a feedback loop, not the assistant. Every `POST /api/health-metrics/sync` emitted socket `health:metrics`; the app answered with `requestHealthRefresh` → every mounted steps/metrics/hydration hook re-read the device (`force`) and synced again → more events, multiplied by each open screen. Guards now (keep all three): server — `/sync` per-user limit 30/min, writes/emits/Quest recompute only when a value actually changed, `emitUserHealthMetrics` coalesced to ≤1 per 3 s per user; app — `requestHealthRefresh` coalesced (1.5 s), socket echo of this device's own sync ignored for 5 s (`isOwnHealthEcho`), identical payloads never re-pushed, device pushes ≤1 per 20 s (`syncNativeHealthToServer`). Never make a socket event trigger a write without these guards.

Voice turn latency (logs: transcribe 4–5 s, plan 4–7 s, speak 1.5–4 s): no extra model call to pick context (`assistantDefaultDomains`), the planner's static system prompt comes first (provider prompt cache) with clock/subject/context in a second system message, recording is speech-grade (16 kHz mono 32 kbps AAC), and recording ends automatically ~1.6 s after the person stops speaking (adaptive noise floor in `useAssistantVoice`); releasing still sends at once.

## Loop guard (2026-09-29, app 1.0.0.17.13)

Two nets for request loops nobody has found yet (after the health-sync incident). App: `mobile/src/lib/requestBreaker.ts`, checked in `request()`, native uploads and `pulseApi` via `guardRequest` — the same method+path+query more than 30× in 10 s is refused locally for 30 s (429 `CLIENT_LOOP_GUARD`), more than 300 requests of any kind in 10 s pauses everything for 30 s; each trip is reported once per 5 min to `POST /api/app/client-guard` (route template only, ids → `:id`, no query). Server: `server/src/lib/loopGuard.js` — a per-session ceiling of 600/min on all of `/api` (`user-ceiling`), keyed by session token hash, guests never counted. This is the only allowed exception to "no global /api limiter": never lower it towards real traffic or key it by IP. Both paths send a throttled Director Telegram notice (search Render logs for `[loop-guard]`). A trip means an app bug: find and fix the loop, do not raise the limits.

Audit follow-ups (1.0.0.17.14): foreground work uses `onReturnToForeground` (`src/lib/appForeground.ts`, background → active only — iOS inactive → active from Face ID / permission sheets / Control Center is not a return); `runPostLoginSideEffects` runs once per account per 5 min unless `force` (sign-in); `runMediNotificationBrain` ≤1/min with one trailing run (`force` for settings changes); push register skips an unchanged token for 6 h; `requestQuestRefresh` is coalesced (300 ms) and socket reconnects refresh with 0–4 s jitter; MEDIRUN background uploads back off 5 s → 5 min; GETs replay once only on 502 (never 503/504). Server: AppSettings cached 10 s, AI daily fuses in `server/src/lib/aiDailyCap.js` for routes outside `enforceAiQuota`, `PHARMACY_SYNC_IN_WEB=off` moves the Playwright scrape out of the web process (only once the cron service is confirmed). New AppState / socket handlers must follow the same rules.

## Server-data cache (2026-09-29, app 1.0.0.17.15)

Owner: pages must not reload everything on every visit, and live values must never stick (steps 400 → 1 000). Server reads go through TanStack Query (`src/lib/queryClient.ts`, hook `src/hooks/useAccountQuery.ts`): stale-while-revalidate, memory only, every key `['acct', accountId, …]`, whole cache cleared on account change. Freshness tiers `FRESH.LIVE` (0 — steps, water, anything that changes by itself: always re-read on focus/foreground, old value stays visible until the new one lands), `SHORT` (30 s — lists the person edits), `LONG` (5 min — news, coach). Hidden stack screens do not refetch (`subscribed: focused`). Writes signal themselves: every successful non-GET in `api.ts` calls `invalidateAfterWrite` (`src/lib/queryInvalidation.ts` maps path prefix → keys) — add new write prefixes there; never add `/api/health-metrics` (device syncs would re-read → re-sync). Migrated: medications, nutrition dashboard + diary, coach, news, cycle view (Home card and cycle screens share `['cycle','view']` via `src/lib/cycleViewCache.ts`; saves put their optimistic view in with `putCycleView`), steps, water, Quest (dashboard LIVE, journey/achievements/rewards; `requestQuestRefresh` = `invalidate('quest')`), records, pets hub/detail; Home/Profile focus re-reads `/auth/me` at most once a minute. POSTs that only read/compute are listed in `READ_ONLY_WRITES` and never invalidate — a screen that calls one after its data loads would otherwise loop (cycle insights). Not yet migrated: pet sub-screens, reward detail/redeem, entitlements (every cycle screen reads `['cycle', …]` keys through `cycleViewCache.ts` / `cycleQueries.ts`, guarded by `tests/cycle-server-cache.test.cjs`). New screens use `useAccountQuery` instead of `useFocusEffect` + `useState` fetching.

## Email system (2026-09-28)

`server/src/lib/email/` (`email.js` re-exports for `passwordReset.js`). Resend over plain fetch (Idempotency-Key, batch, 429 back-off), one branded layout, templates = code defaults (`templates.js`) + admin overrides (`EmailTemplate`), `{{var}}` allow-list per template, HTML-escaped, links https/mailto only. Triggers: `welcome` after email `/register` (setImmediate, once per user via `EmailLog.idempotencyKey`, never blocks sign-up; phone sign-ups have a synthetic `@phone.medicard.ge` login and get nothing), `password_reset`, `account_deleted` (after `DELETE /api/auth/me` commits, not linked to the deleted row). Kill switch = feature flag `email`; per-template `enabled`. `EmailLog` keeps sha256 + masked address only, purged after 180 days (`email-log-purge` lease). Resend webhook `POST /api/email/webhook` (Svix, `RESEND_WEBHOOK_SECRET`, 503 when unset) advances status and suppresses hard bounces / complaints (`EmailSuppression`, transactional included). Marketing needs `User.emailMarketingOptIn` (Law 3144; off by default; raw SQL only — the Prisma fields are `@ignore`), toggled in Profile → Notifications or `/unsubscribe?t=` (signed, RFC 8058 POST). Campaigns: admin `#/email`, worker lease `email-campaigns`, claims each recipient once. Never put health data in an email. Tables: `prisma/20260928-email.sql` via `install-email.mjs` in the release chain. Tests: `server/src/lib/email.test.js`.

## Schema installs on deploy (2026-09-28)

The Render service was created by hand, so it ignores render.yaml's `preDeployCommand`: nothing ran the install scripts and the funnel, email and community tables were missing in production until they were installed manually on 2026-09-28. The dashboard Pre-Deploy Command must be `npm run db:install` — every `server/scripts/install-*.mjs` (additive, idempotent, no seed). Never put `npm run release` there: its `seed` step rewrites package rows and aborts in production when the configured admin does not exist. Every new install script must be added to `db:install` (`server/src/lib/installChain.test.js` fails otherwise).

## Support inbox (2026-09-28)

Mail to support@medicard.ge (Resend Inbound, MX eu-west-1) arrives as `email.received` on the existing Svix-verified `/api/email/webhook` and lands in `SupportThread` / `SupportMessage` / `SupportSnippet` (`prisma/20260928-support.sql`, `install-support.mjs` in `db:install`). Admin page `#/support` (read `SUPPORT_VIEW`, change `SUPPORT_MANAGE`): threads, sanitized HTML in a sandboxed iframe, attachment proxy (no disk), replies from `SUPPORT_FROM` with In-Reply-To/References through the normal mailer (kill switch, suppression, EmailLog), internal notes, snippets, owner notice to `SUPPORT_NOTIFY_EMAIL` (subject only, 1 per 10 min, loop-protected). Reading bodies/attachments needs `RESEND_INBOUND_API_KEY` (a Full-access key; Sending-access keys can only send) — without it the inbox is metadata-only and says so. Inbound content is untrusted: keep it sanitized and never render it as admin page HTML. Closed threads older than 2 years are purged daily. **New letters (2026-10-09):** „ახალი წერილი“ in #/support starts a conversation (`POST /api/admin/support/letters`, preview `/letters/preview`) from `SUPPORT_FROM` or `SUPPORT_LETTER_FROM` (default `George Shengelia <ceo@medicard.ge>`, category `letter` = plain email, no brand chrome). The thread lives in that mailbox, our own `Message-ID` is stored so the answer threads back, and every reply in a thread goes out from its mailbox (`senderForMailbox`; unknown mailboxes answer from support@).

## Server capacity alerts (2026-09-28)

Owner wants to scale Render before the server falls over. `server/src/lib/capacity.js` (production only; `CAPACITY_MONITOR=off` disables) samples each instance once a minute — CPU vs cgroup limit, memory vs limit, event-loop p95, GET `/api` p95 (AI answers/uploads are POST and excluded), 5xx %, DB ping — into `CapacitySample` (7 days) via `prisma/20260928-capacity.sql` / `install-capacity.mjs` in `db:install`. The `capacity-monitor` lease holder evaluates the fleet (`RULES`: a threshold must hold for 2–3 minutes in a row, so deploy/cron spikes do not alert) and sends Director Telegram notices through `notifyOwner` with the concrete Render step (instances N → M for ~60 % CPU, bigger plan for memory, "scaling will not help" for DB/5xx); escalation goes out at once, repeats after 30 min (critical) / 2 h (warn), "recovered" after 10 quiet minutes; history in `CapacityEvent`. Admin `#/capacity` (სერვერის დატვირთვა, `g z`) shows the series, live instances, alert history and a test-alert button. Samples hold numbers only — never users, paths or payloads. Server shutdown drains in-flight requests up to 27 s on SIGTERM (Render kills at 30 s).

## Error monitoring (2026-09-29)

Self-hosted instead of Sentry: `server/src/lib/errorMonitor.js`, table `ErrorEvent` (`prisma/20260929-errors.sql`, `install-errors.mjs` in `db:install`). Inputs: the app's `POST /api/app/client-error` (no auth; a valid user Bearer only attributes the events — never a user id from the body; headers `X-Medicard-Platform` / `X-Medicard-App-Version`; body `{ events: [{ kind: crash|error|unhandled_rejection|render, name, message, stack?, route?, fatal?, at? }] }`, ≤10 events (extra ignored), 202 / 400, own limit 20/min per IP), every unhandled 500 in `middleware/error.js` (fire-and-forget) and `uncaughtException` / `unhandledRejection` in `server.js` (log, record, still exit 1 — up to 2 s later to flush). Scrubbing before storage: message ≤300, stack ≤15 frames as `function (file:line)` with basenames, emails → `[email]`, ≥7-digit runs → `[num]`, JWT/long tokens → `[token]`, UUID/cuid → `:id`, routes via `routeTemplate` (no query); user = 16-hex sha256 hash. Never add bodies, query strings or health data. Fingerprint = sha1(source|kind|name|normalized message|first own frame without line number). Per instance: one row per fingerprint per 10 s (repeats fold into the next row's `count`), ≤500 rows/min. Director Telegram: new fingerprint (not seen in 7 days; ≤1/6 h each, ≤10/h) and spike (>50 in 10 min; ≤1/2 h each); throttles are in memory per instance. Recording is production-only (`ERROR_MONITOR=off|on`); rows purged after 30 days under the `error-events-purge` lease. Admin `#/errors` (შეცდომები, `g g`, `v4/modules/errors.js`, `/api/admin/errors`, `/api/admin/errors/:fingerprint`).

## Module switches + Home news (2026-09-28, app 1.0.0.16.2)

Owner: every module must be pausable from admin without an app build (2026-10-02: „any function“, starting with doctor visits). `server/src/lib/featureFlags.js` `FEATURES` (group module/ai/system; `parent` = child is effectively off while its parent is off, one level only — tested) covers medications, visits, records, labs, hydration, steps, weight, cycle, nutrition(+nutritionAi), medi(+mediDoctor, mediDeep, symptoms, imaging, skin, voice), pets(+mediVet), medirun(+medirunAutopilot), quest(+rewardsStore), coach, community, pharmacy, news, weather, weeklyReport, healthPassport, invites(+referralRewards), email. Server: `requireFeature` on each router answers writes with 503 `FEATURE_DISABLED` + the admin's message — this is all a store build older than 1.0.0.16.2 gets (reads stay open so history is visible); `match` narrows it (Medi modes by `body.mode`, lab AI paths, hydration goal) and `/api/ai/analyze-image` checks its multipart `kind` inside the route. Never block `/api/health-metrics/sync` (phones retry — see the loop incident) and never cancel medication/visit reminders on a pause (a missed dose is worse than a paused screen). Medi (`assistant.routes.js`): `featureForAction` maps tools and `open` destinations to keys; a paused one gets the admin's message instead of a review (`/plan`), 503 on `/prepare`, and `/catalog` leaves it out (`voiceInput`/`voiceOutput` follow `voice`, so older builds hide the microphone too); execution goes through the module's own route, so its `requireFeature` is the backstop. App 1.0.0.16.2+: `/api/app/status` `features` + `featureMessages` → `mobile/src/lib/featureFlags.ts` store (cached, re-polled on foreground ≤1/min, a 503 FEATURE_DISABLED hides the module at once); Home sections/tiles, Explore and Profile blocks disappear and `ModuleGate` covers the module's routes (`featureRoutes.ts` maps route → key); the keys added on 2026-10-02 hide from app 1.0.0.18.16. Web `/app`: routes and nav carry `feature` (`anyOf` for the metrics page). Admin `#/features` groups the switches by theme (`FEATURE_SECTIONS` in `v4/modules/manage.js`; a key missing there falls back by group). A new module = add its key to FEATURES, mount `requireFeature`, map its route in `featureRoutes.ts` (and Medi's `TOOL_FEATURE` / `DESTINATION_FEATURE` when Medi can act there), hide its entries, place it in `FEATURE_SECTIONS` (test `featureRoutes.test.ts` checks keys exist on the server). Whole-app stop = Settings maintenance mode.

Home news („სიახლეები“): admin `#/news` (`v4/modules/news.js`, `/api/admin/announcements`, writes need `NEWS_MANAGE`, audited). Tables `Announcement` / `AnnouncementImage` (bytes in Postgres, public `/api/announcements/image/:id`) / `AnnouncementReceipt` (first view/tap/dismiss per person) — `prisma/20260928-announcements.sql`, `install-announcements.mjs` in `db:install`. Cards sit directly above nutrition (`homeSectionOrder` keeps `news` glued to `nutrition`), flat surface card, tone only tints badge/tile/button (no second spotlight), max 5, detail screen `/news/[id]` (also valid as a push `route`). Buttons open an allow-listed app route (`ROUTE_ROOTS`, identical on server and app — tested) or an https link. Audience = gender + platform only; never health data.
