# MEDIBOOK: catalogue, map, online booking, business panel (/business), admin

Owner request 2026-10-15: „მნიშვნელოვანი ინფრასტრუქტურა“ — every dental clinic, beauty salon, aesthetic centre,
clinic and studio of our consumer segment in one catalogue with a map; MEDICARD users book online with every
step and notification; businesses claim or register themselves at https://medicard.ge/business and run a
Stripe-style panel (calendar, staff, services, clients, discounts, finance, analytics incl. utilisation —
„მარგი ქმედების კოეფიციენტი“). Inspiration: salonkee.be. „ექიმთან ვიზიტები“ became part of MEDIBOOK.
Read this file before working in the area; add new notes here, not in AGENTS.md.

## Names and rules

- Module **MEDIBOOK** (`book`), brand id `book` in `mobile/src/theme/moduleBrand.ts` (lilac `#7A58C9` / `#C6B2F5` — used lightly, lines not fills;
  the first pick, fuchsia, the owner rejected on day one), tone `book` in `colors.ts`. Feature flag `book` (server
  `FEATURES`, app `FEATURE_KEYS`, admin section „სხვა სივრცეები“). `visits` stays: it gates the hand-typed visit
  editor and Medi's visit tools.
- Free for consumers and (for now) free for businesses — no payments anywhere; prices are shown, paid on site.
- Only public business facts travel: name, category, contacts, address, hours, pictures, services, staff names,
  ratings. A client's note is theirs and the business's; never health data. Listing events (`BookEvent`) carry a
  hashed viewer, never a user id.
- Booking needs a verified phone (`requireVerifiedPhone`, the women's-space rule) — the business must be able to
  reach the client; the app offers `/profile/verify-phone` on the 403.
- Reminders for bookings are local notifications (prefix `book:`, same Profile switch as visits — „ვიზიტები და
  ჯავშნები“, family `visits`); the server pushes only changes (confirmed, moved, cancelled) and „შეაფასე“.

## Data (prisma/20261015-medibook.sql, install-medibook.mjs in db:install)

`BookBusiness` (status LISTED catalogue · PENDING registered by an owner, hidden from lists · CLAIMED live with an
owner · HIDDEN by admin; `source` MAPBOX | OSM | OWNER | ADMIN + `sourceRef` unique), `BookImage` (bytes in
Postgres, public `/api/book/image/:id`), `BookMember` (OWNER / MANAGER / STAFF, `staffId` links a member to their
calendar), `BookClaim` (CLAIM of a listed row, REGISTER of a new one; one PENDING per business per user),
`BookStaff` (schedule per weekday, `serviceIds` empty = every service), `BookService` (price / priceTo GEL,
duration, buffer, online), `BookTimeOff`, `BookClient` (the business's CRM row; `userId` when an app user),
`BookDiscount` (PERCENT / FIXED, services, dates, weekdays, hours, code, maxUses), `BookAppointment` (PENDING /
CONFIRMED / CANCELLED / COMPLETED / NO_SHOW; source APP / WEB / BUSINESS; price copied at booking; reminder flags),
`BookReview` (one per appointment, business reply), `BookFavorite`, `BookTransaction` (INCOME written once when an
appointment completes — unique on appointmentId; manual EXPENSE / INCOME), `BookEvent` (VIEW, CALL, ROUTE, WEBSITE,
SHARE, BOOK_START, BOOK_DONE, FAVORITE). Times are TIMESTAMPTZ; the day logic uses a fixed UTC+4
(`lib/book/time.js`). Catalogue ids are `bk-<sha1(source|ref)>`, slugs `<name>-<6 hex>`.

## Wave 2 (2026-10-16): waiting list

- Schema: `BookWaitlist` in `20261016-medibook-2.sql` — business, client (user and/or client row, name, phone), the services (`serviceIds` JSONB + the first `serviceId` + joined `serviceName`), optional person, `fromDate`/`toDate` (YMD), `dayParts` (MORNING < 12:00 ≤ AFTERNOON < 17:00 ≤ EVENING; empty = any), note, status WAITING / OFFERED / BOOKED / CANCELLED / EXPIRED, source, the last offer (`offeredAt`, `offeredStartsAt`, `offeredStaffId`, `offerCount`), `appointmentId` once booked.

## Group classes with seats (2026-10-16, wave 6)

- **Why**: the one segment the engine could not serve was fitness — a yoga class at 18:00 with 15 seats where many clients book the same minute. The FITNESS starter kit already had yoga / pilates / zumba in halls; now a service has `seats` (1 = a normal visit; 2+ = a class) and a slot with seats becomes a class.
- **Model**: one class = one `BookClass` row (business, service, trainer `staffId`, start / end, `seats`, `resourceIds`, status OPEN | CANCELLED, `planned`, note); **every attendee stays a `BookAppointment` row** linked by `classId`. So reminders / SMS (one per attendee), payroll (each attendee's payment), analytics counts, the client history, reviews and the waiting list keep working per person without special cases. The class row is what blocks the trainer's time for every other service and holds the rooms **once** — attendee rows carry `resourceIds = []`. `planned` = the business put it on the calendar (one class from the calendar's „კლასი“ button, or the weekly timetable); FALSE = formed by the first booking of a class service.
- **Data** (`server/prisma/20261016-medibook-6.sql`, `install-medibook-6.mjs` in `db:install`, applied to the main DB 2026-10-16): `BookService.seats` (default 1), `BookService.classSchedule` JSONB (the saved weekly template `{ staffId, weeks, weekly: [{ weekday, time }] }`), `BookClass`, `BookAppointment.classId` (FK, SET NULL when an empty class is deleted).
- **Engine** (`availability.js`, tests): `seatsOf` / `seatsLeft` (seats − live attendees, never below zero), `classBlocks(classes)` (a class as a pseudo booking of its trainer holding its rooms), `classAt(classes, { serviceId, startsAt, staffId })` (the open class at that minute, most seats free first). `slotsForDay` / `daysWithSlots` take `classes`: classes block the grid like bookings; for a class service (`service.seats > 1`, single service — a bundle is never a class) every open class of the day with a free seat is offered as a **join slot** `{ classId, seats, seatsLeft, booked }` to its own trainer (never to anyone else), respecting lead time; `service.scheduled` (= the service has a *planned* class ahead, `context().scheduledServiceIds`) turns the free grid off, so a service with a timetable offers only its planned classes. Without a timetable the grid stays and the first booking forms the class („grid mode“).
- **Bookings** (`bookings.js`): `context()` loads `classes` (`classRows`, with the live `booked` count) and `scheduledServiceIds`; `bundleOf(services, links, scheduledServiceIds)` carries `seats` / `scheduled`; `availability` responses carry `seats` and `scheduled`. `createAppointment`: a class service in a bundle → 400 `CLASS_ALONE`; `classAt` finds the class of that minute (a chosen person must be its trainer, „anyone“ lands in it) → full → 409 `CLASS_FULL` (a forced walk-in by the business may overbook); joining skips the room check and the person clash (the class holds them); otherwise the normal checks run against `[...appointments, ...classBlocks(classes)]`, the first booking INSERTs the `BookClass` row (`planned = FALSE`) and the attendee row gets `classId` and no rooms. `updateByBusiness`: an attendee's own row is **never moved or given another service** (409 `CLASS_MEMBER` — the class moves as a whole, or cancel and rebook); restoring a cancelled seat needs the class open with a seat free (`CLASS_CANCELLED` / `CLASS_FULL`); a plain booking's move and room checks see classes as blockers. `appointmentPublic` adds `classId`, `classSeats`, `classBooked` (`CLASS_JSON` on `APPOINTMENT_SELECT`). `analyticsRaw` returns the period's open `classes`.
- **Classes** (`server/src/lib/book/classes.js`, tests `classes.test.js`): `listClasses({ from, to, staffId?, serviceId? })` (every status, with `attendees`), `classDetail`, `createClass` (service with seats ≥ 2 or `seats` given, an active trainer, one class per service + trainer + minute → `CLASS_EXISTS`, trainer clash → `SLOT_TAKEN`, full room → `RESOURCE_TAKEN`, `force` skips; `planned = TRUE`), `scheduleClasses({ weekly, weeks ≤ 12, seats? })` = the **„განრიგი“ helper**: `normalizeWeekly` + `expandWeekly` (pure: the next weeks' occurrences after now) → `createClass` per occurrence, skipped ones listed with their code (a second run creates nothing twice), the template saved on the service; `updateClass` (move start / trainer — every live attendee row follows with reminder flags reset; `seats` never below the attendees in → `CLASS_SEATS_TAKEN`; note; `status: 'CANCELLED'` cancels every live attendee with the reason) returns the touched attendees with `previousStatus` for the pushes; `deleteClass` only when no live attendee (`CLASS_NOT_EMPTY`). `classPublic` carries `label` „7 / 15“, `seatsLeft`, `planned`, `resources`, `servicePrice`.
- **Routes** (business, under `/:businessId`): `GET /classes?from&to&staffId&serviceId`, `GET /classes/:id`, `POST /classes` (manage), `POST /classes/schedule` (manage → `{ created, skipped, template }`), `PATCH /classes/:id` (manage; notifies every attendee of a move / cancellation like a single booking — push for app users, SMS for the rest — and offers the old day to the waiting list, `waitlistOffered` in the answer), `DELETE /classes/:id` (manage). Seats are taken through the existing `POST /appointments` (consumer and walk-in): the class service at that start joins. `POST|PATCH /services` accept `seats`; `store.listServices` returns `classSchedule`; `servicePublic` (consumer too) carries `seats`.
